# PRD.md — 2D Action Platformer (C++)

## 1. Project Overview

**Working title:** Riftbound: Echoes of Ember  
**Project type:** 2D side-scrolling action platformer  
**Primary language:** C++ (C++17 or newer; C++20 preferred)  
**Target platforms:** Desktop (Windows, macOS, Linux) and modern desktop browsers through WebAssembly  
**Web hosting:** GitHub Pages  
**Engine / framework:** raylib for rendering, input, audio and basic game utilities; CMake for builds; Emscripten for the browser build.

### Product vision

Create a polished, responsive 2D action platformer in which the player explores side-scrolling levels, defeats enemies using melee and ranged weapons, avoids environmental hazards, collects upgrades and fights distinct bosses. The project must be implemented primarily in C++, with clear separation between gameplay systems and platform-specific code.

The same gameplay codebase must support:

1. A native desktop build for full development and debugging.
2. A WebAssembly build that runs in a browser and can be hosted as static files on GitHub Pages.

**Platform constraint:** GitHub Pages only hosts static web assets. The browser build must run through WebAssembly and browser APIs. It cannot use native operating-system process access or desktop-only APIs. Keep platform-specific functionality behind small interfaces.

---

## 2. Goals and Non-Goals

### Goals

- Deliver a complete, playable 2D platformer with keyboard controls.
- Implement responsive player movement, jumping, gravity, collision and combat.
- Include multiple enemy types with readable behaviors.
- Include at least two weapon styles with distinct attack behavior.
- Build multiple levels with checkpoints, collectibles and hazards.
- Include at least one multi-phase boss encounter.
- Provide title, pause, settings, game-over and victory screens.
- Save basic progress and settings where supported.
- Build and deploy the browser version to GitHub Pages automatically.
- Keep the project modular, testable and documented.

### Non-goals for the initial release

- Online multiplayer or network play.
- A level editor for end users.
- Full 3D graphics or physics.
- Procedural generation of every level.
- User accounts, cloud saves or a backend server.
- Mobile touch controls in the first milestone.
- A complex cinematic or voice-acting pipeline.

---

## 3. Target Players and Core Experience

**Target audience:** Players who enjoy compact action platformers with precise movement, readable combat and progressively challenging levels.

**Core experience:** Move through a level, learn enemy patterns, use movement and weapons to overcome threats, collect upgrades, reach checkpoints and defeat the level boss.

### Core gameplay loop

1. Enter a level from the world/level selection screen.
2. Traverse platforms, gaps, hazards and enemy encounters.
3. Fight enemies using the available weapons.
4. Collect health, ammunition/energy and upgrade items.
5. Activate checkpoints.
6. Reach the boss arena and learn the boss attack patterns.
7. Defeat the boss, unlock the next level and save progress.

## 5. Functional Requirements

### 5.1 Game states and navigation

Implement a state machine with at least:

- `Boot` / asset loading
- `MainMenu`
- `LevelSelect`
- `Playing`
- `Paused`
- `Settings`
- `GameOver`
- `LevelComplete`
- `Victory`

Requirements:

- State transitions must be explicit and safe.
- Pausing must stop gameplay updates while keeping the pause UI responsive.
- Returning to the menu must release or reset level-owned resources correctly.
- Invalid state transitions must be handled without crashing.

### 5.2 Player character

Implement a controllable player with:

- Left/right movement.
- Acceleration and deceleration for responsive but controlled movement.
- Variable jump height (short tap versus held jump, within configured limits).
- Coyote time and jump buffering to improve platforming feel.
- Gravity and terminal fall speed.
- Ground detection and stable landing.
- Optional wall contact and wall-jump only if it fits the chosen level design.
- Facing direction based on movement/aim direction.
- Health, damage response, temporary invulnerability and knockback.
- Animation states: idle, run, jump, fall, attack, hurt and death.
- Respawn at the latest activated checkpoint.

Player movement and physics values must be centralized in a tunable configuration rather than scattered magic numbers.

### 5.3 Physics and collision

Implement a deterministic, frame-rate-independent physics/update approach.

Required:

- Delta-time-based movement.
- Gravity, velocity and position integration.
- Axis-separated collision resolution or another documented stable AABB collision approach.
- Collision against solid platforms and level boundaries.
- One-way platforms where required by level design.
- Trigger volumes for checkpoints, collectibles, exits and hazards.
- Damage volumes for spikes, projectiles and enemy attacks.
- Knockback and temporary invulnerability handling.

Requirements:

- Prevent the player from tunneling through normal level geometry at expected game speeds.
- Avoid repeated damage every frame while overlapping a hazard; use cooldowns or enter/exit tracking.
- Keep collision geometry independent from sprite artwork.
- Provide debug rendering for hitboxes and collision boxes, toggleable in development builds.

A full rigid-body physics engine is not required. Use a focused platformer physics implementation.

### 5.4 Combat and weapons

Include at least two distinct weapons:

**Weapon A — Ember Blade (melee)**
- Short-range attack arc or hitbox.
- Attack cooldown and attack animation.
- Damage and knockback.
- Prevent one swing from damaging the same enemy repeatedly unless explicitly intended.

**Weapon B — Pulse Bolts (ranged)**
- Projectile creation and movement.
- Projectile lifetime and collision.
- Configurable damage, speed and cooldown.
- Projectile cleanup when off-screen or expired.
- Optional limited energy/ammunition with pickups.

Combat requirements:

- Clear feedback when the player or an enemy takes damage.
- Invulnerability/cooldown rules to prevent damage stacking in a single frame.
- Weapon switching through a documented control.
- Enemies and bosses must respond consistently to damage.
- All weapon values must be configurable.

### 5.5 Enemy system

Create a reusable enemy base/interface and implement at least three enemy archetypes:

1. **Patroller:** walks between bounds, turns at edges or walls and damages the player on contact.
2. **Ranged Sentry:** maintains a firing interval and launches projectiles toward the player or a predicted position.
3. **Chaser:** detects the player within a configurable range and moves toward them while respecting platforms and obstacles as appropriate.

Each enemy must support:

- Health and damage handling.
- Idle/patrol/attack/hurt/death states as applicable.
- Collision and damage rules.
- Configurable movement and attack parameters.
- Death cleanup and optional score/loot drops.

Enemy behavior should be state-based and understandable. Avoid random, unfair attacks that cannot be anticipated by the player.

### 5.6 Boss fights

Implement at least one boss with a dedicated arena and a minimum of three readable attack patterns.

Example boss: **The Ashen Warden**

- Phase 1: ground slam with a visible warning zone.
- Phase 2: horizontal projectile volley.
- Phase 3: charge attack or rotating hazard pattern.

Boss requirements:

- Dedicated health bar and phase indicator.
- Telegraph or warning before high-damage attacks.
- Clear vulnerability windows.
- Arena boundaries that prevent leaving the encounter unintentionally.
- Boss state machine with idle, telegraph, attack, recovery, hurt and defeated states as needed.
- Victory transition only after boss defeat is confirmed.
- Boss reset behavior when the player dies must be defined and tested.

### 5.7 Levels and world progression

Create at least **three playable levels** for the first complete release:

- Level 1: movement and combat tutorial; basic platforms and patrolling enemies.
- Level 2: more vertical traversal, hazards and ranged enemies.
- Level 3: advanced platforming and the boss arena.

Level requirements:

- Tile/grid-based or data-driven level layout.
- Solid platforms, one-way platforms where needed, hazards and decorative elements.
- Spawn point and exit/goal trigger.
- Enemy placements and collectible placements defined in level data.
- Checkpoints.
- Level completion condition.
- Camera follow with configurable look-ahead and boundary clamping.

Keep level data separate from game logic. Use a simple readable format (for example JSON or a small custom text format) only if it is practical for the chosen implementation. A compiled-in level representation is acceptable for the first prototype, but the architecture should not make future data-driven levels difficult.

### 5.8 Collectibles and progression

Include:

- Health pickup.
- Weapon energy/ammunition pickup.
- Upgrade collectible or score item.
- Checkpoints.
- Unlocking the next level after completion.

Persist only essential data:

- Highest unlocked level.
- Best completion state or score, if implemented.
- Audio and control settings.

For browsers, use an Emscripten-compatible persistent storage approach (such as IDBFS) if persistence is included. The game must still work if browser storage is unavailable; show a clear message or fall back to session-only progress.

### 5.9 User interface and accessibility

Implement:

- Main menu: Play, Level Select, Settings, Quit/Return as platform-appropriate.
- In-game HUD: health, weapon, energy/ammunition, boss health when applicable.
- Pause menu: Resume, Restart Level, Settings, Main Menu.
- Game-over screen: Retry, Main Menu.
- Level-complete and victory screens.
- Settings: master/music/SFX volume and key-control reference; remapping is optional.

Accessibility/usability:

- Readable text and adequate contrast.
- Controls displayed in the game.
- Do not communicate damage or danger using color alone.
- Provide adjustable audio levels.
- Support window resizing and browser canvas resizing without distorting the game world.

### 5.10 Audio and visual effects

- Background music per level or area where available.
- Sound effects for movement, jump, attacks, hits, pickups, checkpoint and boss events.
- Particle effects for impacts, projectiles and collectibles.
- Screen shake should be subtle and configurable or disableable.
- Use original assets or assets with licenses that permit redistribution and web hosting.
- Include an `ASSETS.md` file documenting asset source, author and license for every third-party asset.
- Do not use copyrighted characters, music, sprites or other material without permission.

- Ensure the game can be played entirely with a keyboard.

## 7. Non-Functional Requirements

### Performance

- Target smooth 60 FPS on a typical modern desktop browser and entry-level desktop computer, subject to asset and hardware limits.
- Avoid per-frame heap allocations in frequently executed update paths where practical.
- Reuse projectile/particle objects or use simple pooling if profiling shows allocation overhead.
- Cull off-screen decorative and nonessential objects where useful.
- Keep texture and audio memory usage reasonable.

### Reliability

- No crashes during normal play, level transitions, death/respawn or menu navigation.
- Missing optional audio or visual assets should produce a useful error and graceful fallback, not an uncontrolled crash.
- Clean up resources and entity references safely.
- Avoid dangling pointers and ownership ambiguity; prefer RAII and clear ownership using values, `std::unique_ptr` or other appropriate C++ techniques.

### Code quality

- Use clear class/module boundaries and consistent naming.
- Separate update logic from rendering.
- Avoid giant `main.cpp` files and tightly coupled global state.
- Use `const` correctness and appropriate type safety.
- Add comments for non-obvious physics and collision decisions.
- Keep all tunable gameplay values in configuration structures or data files.

### Suggested module responsibilities

- `Game`: owns the main loop, game state and high-level transitions.
- `AssetManager`: loads and releases textures, sounds and fonts.
- `InputManager`: maps keyboard/mouse input to game actions.
- `Player`: player state, movement intent, health and animation state.
- `Enemy` and enemy subclasses/components: enemy behavior and combat response.
- `Weapon` / `Projectile`: weapon behavior and projectile lifecycle.
- `PhysicsWorld`: gravity, movement integration and collision resolution.
- `Collider` / `Hitbox`: collision geometry and overlap tests.
- `Level` / `LevelManager`: level data, spawning, checkpoints and exits.
- `CameraController`: follows the player and clamps to level bounds.
- `Boss`: boss phases, attack telegraphs and arena logic.
- `HUD` / `Menu`: interface rendering and input.
- `SaveSystem`: progress and settings persistence behind a platform-aware interface.

Use entity IDs or safe ownership patterns for references between entities. Avoid storing raw pointers to objects that may be deleted unless lifetime is explicitly controlled.

## 9. GitHub Pages and WebAssembly Deployment

### Deployment approach

GitHub Pages cannot run a native C++ executable. Compile the C++ game to WebAssembly using Emscripten and publish the generated static browser files.

The deployed output should include the generated HTML loader, JavaScript glue, `.wasm` binary and any required packaged assets/data. The precise filenames are produced by the build system and must be referenced consistently by the generated HTML.

### Required web behavior

- The game loads from the GitHub Pages project URL, including repositories hosted under a subpath.
- Asset paths must be relative or correctly account for the configured Pages base path; do not assume the site is hosted at `/`.
- The canvas scales to the available browser viewport while preserving the intended aspect ratio.
- Show a loading screen while WebAssembly and assets initialize.
- Show a useful error state if WebAssembly fails to load.
- Include a visible fullscreen option where browser support permits.
- Do not depend on server-side APIs.
- Browser audio must begin only after an allowed user interaction where required by browser policies.

### Build targets

CMake should expose distinct targets or documented presets for:

1. `native`: desktop executable.
2. `web`: Emscripten/WebAssembly output for static hosting.
3. `tests`: unit tests for independent game logic.

Keep platform-dependent code limited to initialization, storage and other unavoidable browser/desktop differences.

### GitHub Actions deployment

Create a GitHub Actions workflow that:

1. Checks out the repository.
2. Installs or activates a documented Emscripten SDK/toolchain.
3. Configures CMake for the Emscripten target.
4. Builds the web target.
5. Copies or stages the generated web output into the Pages artifact directory.
6. Uploads the Pages artifact.
7. Deploys it using the official GitHub Pages deployment actions.

Use the current supported GitHub Pages Actions workflow pattern and least-privilege workflow permissions. Do not hardcode a personal token. The workflow must fail clearly if the web build does not produce the expected HTML and WebAssembly files.

Document the repository settings required to enable GitHub Pages with GitHub Actions as the source.

### Local web testing

Document commands to run a local HTTP server against the generated web output. Do not recommend opening the generated HTML directly with `file://`, because browser loading of WebAssembly and assets may require HTTP serving.

## 11. Development Phases

Implement in small, verifiable milestones. Do not attempt to build the entire game in one generation step.

### Phase 1 — Project foundation

- Create CMake project and folder structure.
- Integrate raylib.
- Create a resizable game window and main loop.
- Add game state handling and basic logging.
- Confirm a clean native build.

**Exit condition:** Native application opens, updates and renders without errors.

### Phase 2 — Player movement and physics

- Implement player movement and jump controls.
- Implement gravity and collision resolution.
- Add camera follow and level boundaries.
- Add debug hitbox rendering.

**Exit condition:** A test level supports reliable movement, jumping and platform collision.

### Phase 3 — Combat and enemies

- Add melee and ranged weapons.
- Add projectile lifecycle and hit detection.
- Implement three enemy archetypes.
- Add health, damage, knockback and death handling.

**Exit condition:** Player can fight and defeat each enemy type reliably.

### Phase 4 — Levels and progression

- Build three levels.
- Add hazards, collectibles, checkpoints and exits.
- Add level selection/unlock progression.

**Exit condition:** Player can finish the first two levels and reach the boss level.

### Phase 5 — Boss and game flow

- Implement boss arena and multi-phase boss state machine.
- Add HUD, menus, pause, game-over and victory screens.
- Add progress/settings persistence.

**Exit condition:** A complete game run from main menu through boss victory is possible.

### Phase 6 — Polish and quality

- Add and document licensed art/audio assets.
- Add animations, particles and feedback.
- Tune difficulty and controls.
- Add tests and fix bugs.

**Exit condition:** Core acceptance criteria pass on the native build.

### Phase 7 — WebAssembly and GitHub Pages

- Configure Emscripten build.
- Verify browser input, rendering, audio and persistence.
- Add GitHub Actions build/deployment workflow.
- Deploy to GitHub Pages and test the public URL.

**Exit condition:** Browser build works from the repository's GitHub Pages URL, including asset loading from a project subpath.
